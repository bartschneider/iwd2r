## Notes

Ported from the Ghidra listing and the disassembly (0x7AF1C0-0x7AF3AF, `ret 0xc`): the fast 16-bit
blit of the whole frame - the 8-bit frame's indices through the realized 16-bit palette
(`CVidImage::rgbTempPal`, one WORD a pixel), the transparent index skipped, the rows bottom-up by
`lPitch` in bytes. It is the 16-bit twin of the fast `Blt8To32` (0x7CFBC0): unlike that one it has no
`nTransVal` (the palette is realized with a fixed 255) and no `g_pChitin->field_174` block, exactly
as the ported 24-bit sibling `sub_7CECD0` has none. Called by both `CVidCell::Render` overloads for
the dispatcher's `else` column at 16 bpp (0x7AEA9C, 0x7AEDE3). NOTE: the survey (report-T50.md) names
it `Blt8To16` after that role; the export has only the address, so the code keeps the stub's
`sub_7AF1C0` and the two Render call sites stay untouched (the same choice the 24-bit sibling made).
The 6-argument `CVidCell::Blt8To16` at 0x7AF3C0 is the clipped overload.

The setup:

- a zero width or height returns TRUE before anything;
- `SetPalette(pRes->m_pPalette, 256, TYPE_RESOURCE)` unless `m_bPaletteChanged` (0xCC);
- `Realize(rgbTempPal, 16, dwFlags, &m_paletteAffects, 0xFF)`;
- with `!m_bShadowOn` the shadow entry (index 1) takes the video mode's `field_24`: **only its low
  word** (`mov word ptr [4*ecx + 0x9064f8], ax` at 0x7AF262; the 32-bit sibling writes the full
  DWORD), so the port masks what is there;
- `GetFrameData` then the ChVidImage.cpp:2396 `pData != NULL` assert, the BAM header's transparent
  index, and `lPitch - width * 2` as the row step added to a byte pointer.

Two walks, as the 32-bit template:

- compressed: the run-length stream with the transparent index as the command byte (the next byte
  is the run minus one); runs may span rows and the original's unrolled skip is the same algorithm
  as the per-row handling `Blt8To32` and the 24-bit sibling use (w3 verified that on 0x7CECD0).
  One quirk is this function's own: the row's continuation after a drawn pixel is `ja` at 0x7AF358,
  which reads the **carry left by the transparent-index `cmp`** (`dec` does not set CF), so a drawn
  palette index **below the transparent index ends the row early** - as if the width were used up,
  the rest of the stream goes to the next row's start (and is dropped if that was the last row).
  The 24- and 32-bit siblings use `jne` there and do not have it. The oracle run found this (RLE
  inputs diverged at the first index under the transparent byte); the unit test pins it;
- uncompressed: each pixel is `pFrameData[1]`, i.e. **one byte ahead** of the pointer (0x7AF384:
  `mov al, byte ptr [esi + 1]`), unlike the 24- and 32-bit siblings, which read `[esi]`. The whole
  frame therefore lands shifted by one palette index and the last pixel of the last row reads one
  past the frame's data. Kept as the bytes have it; the oracle case draws raw frames against it,
  and the unit test pins the shift.

Each drawn pixel is `*pSurface = (WORD)rgbTempPal[index]`: the listing's
`*(ushort *)(&DAT_009064f8 + index)` is a byte stride, but the instruction is
`mov dx, word ptr [ebx + 4*eax]` (0x7AF34C) - DWORD entries, low word stored - which is what the
port does. Nothing in the function draws `rand()`.

## Oracle

`vid/cell_blt8to16_fast` (oracle/cases/vid.cpp): a synthetic BAM (a zeroed `CResCell` holding the
parsed flag, header, palette and one frame entry; the data raw or RLE), random frames up to 8x4
with the transparent index mixed in and index 1 present, the palette flags, the cell's shadow on
and off and the mode's shadow colour, drawn at (8, 8) of a 64x64 16-bit canvas of random bytes, on
5-6-5 and 5-5-5 in turn (the realization reads the mode's masks). The whole canvas and the result
are compared. The unit test (`tests/test_vid.cpp`, "blt8to16_fast") pins the walk, the row step, the
shadow entry, the raw walk's one-byte lead and the early row end on both mask layouts.

Run on our Windows rig (runner built from this branch, `--file vid`), verbatim:

```
  vid/cell_blt8to16_fast           passed (1800 inputs, 0 failures)
  ...
  54 passed, 0 expected failures or crashes, 0 pending, 0 unexpected; run PASSED
```

The first run failed 692 of the 1800 inputs, all on RLE frames; a word-level diagnostic
showed the original ending each row at the first drawn index below the transparent byte - the `ja`
quirk ported above. With it the whole file passes.
