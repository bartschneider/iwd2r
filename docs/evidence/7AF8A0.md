## Notes

Ported from the Ghidra listing and the disassembly (0x7AF8A0-0x7AFB43, `ret 0xc`): the clear-shadow
blit of a whole frame - the 8-bit frame's indices through the realized 16-bit palette
(`CVidImage::rgbTempPal`, one WORD a pixel), the transparent index skipped, rows bottom-up by
`lPitch` in bytes. It is the 16-bit twin of `Blt8To32ClearShadow` (0x7D0470) and the sibling of the
fast `sub_7AF1C0`: same palette setup (`SetPalette` unless `m_bPaletteChanged`, then
`Realize(rgbTempPal, 16, dwFlags, &m_paletteAffects, 0xFF)`), same `lPitch - width * 2` byte row
step, and with `!m_bShadowOn` only the low word of `rgbTempPal[SHADOW_ENTRY]` takes the mode's
`field_24` (0x7AF932). Called by both `CVidCell::Render` overloads for the
`(dwFlags & 0x4) && TRANSLUCENT_SHADOWS_ON` column. NOTE: the survey (report-T50.md) names it
`Blt8To16ClearShadow`; the export has only the address, so the code keeps the stub's `sub_7AF8A0`
and the Render call sites stay untouched.

The shadow rules differ by walk and by the cell's flag:

- `m_bShadowOn` set: the mode's half mask is `(Rmask >> 1 & Rmask) + (Gmask >> 1 & Gmask) +
  (Bmask >> 1 & Bmask)` (0x7AF93C-0x7AF966), which halves every channel and clears the bit shifted
  into the next one. The compressed walk uses it for index **1** only (0x7AF9F3-0x7AFA02); the raw
  walk for any index **below two** (`cmp eax, 1; ja` at 0x7AFADB), so index 0 is a shadow pixel too
  when the transparent index is not 0.
- `m_bShadowOn` clear: the shadow entry was replaced by the mode's shadow colour and the frame is
  drawn plainly. The raw walk does that. The compressed walk, however, halves the palette value
  with `[ebp-0x14]`, the half mask it computes only in the shadow-on path - an **uninitialized
  read** (0x7AFA6C with no store on that path). This port writes the realized palette there, as the
  32-bit sibling does, and the oracle case never runs that path: the original has no defined
  behaviour to compare. The unit test pins the port's choice.

Unlike `sub_7AF1C0`, this function has neither of that port's 16-bit-only walk quirks: the raw walk
reads `[esi]` (no one-byte lead) and both compressed walks continue with `jne` (no `ja`-after-`dec`
early row end). It also has **no zero-size guard at all**: its do-while loops would spin on an
empty frame (Render never passes one), so the port returns TRUE there with a NOTE.

Nothing in the function draws `rand()`.

## Oracle

`vid/cell_clear_shadow16` (oracle/cases/vid.cpp): a synthetic BAM (zeroed `CResCell` with the
parsed flag, header, palette and one frame entry; data raw or RLE), random frames up to 8x4 with
the transparent index mixed in and index 1 present, the palette flags and the mode's shadow colour,
drawn at (8, 8) of a 64x64 16-bit canvas of random bytes, on 5-6-5 and 5-5-5 in turn (the
realization and the half mask read the mode's masks). Compressed frames always run with the cell's
shadow on - the shadow-off compressed path reads the original's uninitialized half mask. The whole
canvas and the result are compared. The unit test (`tests/test_vid.cpp`, "clear_shadow16") pins the
walk, the shadow halving for index 1 (compressed) and below two (raw), the shadow-off plain palette
and the zero-size guard on both mask layouts.
