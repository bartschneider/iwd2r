## Notes

disagreed with WSO at e8dd16a: his full body deletes our three ReplayWaitForSearch calls (replay-only, no-op without IWD2R_STATE_DUMP — removing them re-opens the walk_and_talk divergences the paragraph below documents) and narrows pointer handles with a plain `reinterpret_cast<LONG>`, but his song-guard hunk is right: the exe tests `m_nCurrentSong` (area +0xae8, `song != 1` at 0x6F75xx outer, `song != 0` inside the night branch) so PlaySong(-1, 0x4|0x2) runs once per day/night transition, where ours re-played and reset the 600 counter on every update; guard adopted (`IsDay() && m_nCurrentSong == 1` / `IsNight() && m_nCurrentSong == 0`), the rest of our body kept; case readout-46E3D0 decides.

The area's AI step: the picked object under the cursor, then for every object of the front, middle and back vertical lists (tail to head) a share, DoAIUpdate (the AI speed gate) and, when it answers TRUE, a deny for the object's AIUpdate. Only the replay-mode addition is new in vis-probe round 7; the original's code is unchanged.

iwd2r addition (no counterpart in the original): after each object's AIUpdate and ReleaseDeny, ReplayWaitForSearch (a no-op unless IWD2R_STATE_DUMP is set, platform/replay.h) waits until the path search the update queued is done. The search thread spins on the requester's share while the update holds its deny (SearchThreadMain 0x5492E0 retries GetShare on DENIED), so it snapshots the search map (SnapshotInit) when the deny is released, before the next object moves, and in every recording of the original the result is DONE at the requester's next update. Without the wait the timing in ours depended on scheduling: the result came a few frames late, or the snapshot after later objects had moved, and about one run in five of walk_and_talk diverged (first seen at frames 2490-2520, 2550-2580 and 3240-3270, numbered before 1aef7608 added 20 frames after opening_done, each at a search's first poll). With it 15 of 15 runs gave the original's ai_rng_state at door_open.

The wait is a deviation, and in replay it rules out what the original allows while the next object's update runs beside the search:

- FindPath (0x51E150 CPathSearch::FindPath) is never cut short at minNodes by another request: its two node-limit tests go past minNodes only while m_searchRequestListEmpty is set, and queueing a request clears it, but the next object queues nothing until the search is done.
- A share the search thread asks for never comes back DENIED because the next object's update holds that object's deny. In the original, 256 DENIED tries drop a party member (or a target) from the search's goals and snapshot.
- Only the requests queued in the three per-object loops are waited for. A request queued anywhere else (the message handler, the main thread) is not.

The wait has a deadline of 5 s of real time (platform::replay::WaitForSearch). SearchThreadMain can lose a semaphore post: after a NO_TARGET, ERROR or STALE result it has released field_1B58, so its last list test and its ReleaseSemaphore/WaitForSingleObject tail run without the lock, and the semaphore's maximum is 1. A request queued in that window then waits for the next post, and with no search thread it waits for ever. On expiry the wait writes one stderr line (the object, its request's state, the list lengths) and counts it in the dump's search_wait_timeouts, and tools/oracle.py fails the checkpoint. After the first expiry, and when there is no search thread, one poll decides, so the run goes on to its dumps.
