# 0x5BFE10 CInfGame::SetProtagonist

## Why ours was kept

The batch row flags WillScarlettOhara's fork (iwd2-re@e8dd16a750966af53f24daaf49dcb4fb13594c13,
read through git plumbing) as changed against our base body. Diffing his body
against ours shows the only differences are a single member rename: he reads the loaded-dialog flag as ``m_bDialogActive`` where we read ``field_54`` - the same ``CGameDialogSprite`` byte at +0x54..

His body:

```c
if (g_pBaldurChitin->m_pEngineWorld->m_internalLoadedDialog.m_bDialogActive) {
    nId = g_pBaldurChitin->m_pEngineWorld->m_internalLoadedDialog.m_characterIndex;
}
```

Ours is identical but names the flag ``field_54``. ``m_bDialogActive`` does not
exist in our headers; ``field_54`` is declared in ``CGameDialogSprite``
(``/* 0054 */ unsigned char field_54;``, CGameDialog.h) and
``m_internalLoadedDialog`` sits at 0xEB0 in CScreenWorld (CScreenWorld.h:167),
so our access already lands on the exe's flag byte.

## The exe reading

Bundle decompile: ``if (*(char *)(*(int *)(DAT_008cf6dc + 0x1c88) + 0xf04) != '\0')
{ param_1 = *(int *)(... + 0xee0); }`` - a char test at engine+0xF04, then the
index read at engine+0xEE0. With ``m_internalLoadedDialog`` at 0xEB0 that is
exactly +0x54 (the flag) and +0x30 (``m_characterIndex``, CGameDialog.h:69).
Same two fields ours reads; only his label differs.

Ours already matches the exe; adopting his naming would need header edits
outside this batch's owned files. Kept as ours.
