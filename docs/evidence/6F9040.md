## Notes

Changed against the decompile and the disassembly (0x6F9040):
- A collision search's delay counts down (`dec cl; mov [eax+1], cl` at 0x6F90EA); the port decremented the request pointer instead.
- The next node is taken only when the sprite has reached the current one (its 8 x 6 cell, or no nearer than last frame), inside that test; the port advanced a node every frame and walked past the path's end into whatever memory followed.
- The step is computed in the 4/3-scaled space of m_posExact: the destination's y there is node.y * 16 + 8 (not the pixel y), the distance is the truncated (__ftol) square root, and for a move scale of 9 or more the distance is divided into steps ((scale / 2 + distance) / scale, at least 1) with the delta not multiplied by the move scale again; below 9 the delta is distance-scaled by the move scale. The port mixed pixel and scaled y, rounded the root and multiplied twice.

Exemption: needs a sprite walking in an area with the search thread and the message handler; covered by the Catch2 tests "[move] a sprite walks ..." and "... sent into a wall ..." and the walk_and_talk replay's `moved` checkpoint.
- Fix round 1: with no path (`m_pPath == 0`) the walk ends at 0x6F95A6 on every route, with or without a search request; the port returned only when a request had just been handled, so an idle sprite ran the arrival test and stepped every AI update, and a sprite whose path was dropped mid-walk kept stepping and finally read the NULL path.
- Fix (vis-probe round 3): the footstep's table index (0x6F9F8A-0x6F9FCB) reads the search map at ptOldSearch itself, which is already in search squares: `GetBitCount(TRUE) == 8 ? GetPixelValue(x, y, TRUE) >> 4 : GetPixelValue(x, y, TRUE)` on m_pArea->m_search's bitmap, with no division. Ours called CSearchBitmap::GetTableIndex, the inlined helper as InitializeWalkingSound (0x71DD20) uses it, which divides a pixel position by the square size first, so ours read the square at (x / 16, y / 12) of an already divided point: a wrong terrain, usually no footstep sound and no rand() (walk_and_talk frame 2480, Screed's walk: the original's GetSndWalk draw at +0x89).
- Fix (vis-probe round 3): the distance to the next node is rounded, not truncated. 0x6F97FA-0x6F981A: fild of dx * dx + dy * dy, sqrt (0x7E8034), `fadd QWORD [0x848DD0]` (0.5), then __ftol (0x7E812C): (int)(sqrt(d) + 0.5). Ours dropped the 0.5, so a diagonal of 16 by 16 (22.6) gave 22 instead of 23, and with a move scale of 9 the step count (scale / 2 + distance) / scale was 2 instead of 3: the sprite walked a third faster on that leg (walk_and_talk frame 2484, Screed: 8 pixels a step against the original's 5 to 6).
