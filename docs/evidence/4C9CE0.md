## Notes

Ported from the disassembly (objdump -M intel of the vanilla exe, excerpts
below); Ghidra's control flow around the party loop and the budget checks is
garbled. The second argument is a BYTE (`mov al,[esp+0x90]`), not an INT;
the header now says so. Its only caller, CMessageSpawnPtSpawn::Run
(0x50B120), passes 0.

Offsets: this+0x6E is m_spawningObject, so 0xE2 m_randomCreatureNum, 0xE4
m_difficulty, 0xE8 m_wFlags, 0xEA m_lifeSpan, 0xEE m_huntingRange, 0xF0
m_followRange, 0xF2 m_maxTypeNum, 0xF4 m_activated, 0xF6
m_timeOfDayVisible; 0x136 field_136 (spawned once), 0x137 m_terrainTable.
The game (g_pBaldurChitin+0x1C54) gives m_worldTime.m_gameTime (+0x1B78),
the portraits (+0x382E, count +0x3846, GetCharacterId inlined with
INVALID_INDEX 0x851878), the object array (+0x372C) and m_group (+0x3884).
The sprite gives m_id (+0x5C), m_derivedStats (+0x920, GetLevel 0x4473A0),
m_derivedStats.m_nXP (+0x984, the CRE's current-XP field) and
m_animation.m_animation (+0x50F0).

The flow:

1. Gates, each returning without setting field_136: m_activated is 0;
   field_136 is set and m_wFlags bit 0 is set (spawn once); the current
   hour's bit in m_timeOfDayVisible is clear (the hour is
   GetCurrentHour inlined: gameTime % 108000 / 15 / 60 / 5); the spawn
   point's own visibility tile is visible.
2. A total level of 0 is replaced by the sum of the portraits' levels
   (GetShare, CDerivedStats::GetLevel, ReleaseShare), added into the BYTE.
3. The budget is `m_difficulty * level / 100` (unsigned). There is no
   per-level table: the "table" of Review Focus 5 is this product.
4. One creature index for the whole call: `rand() % m_randomCreatureNum`,
   or 0 with no creatures (no rand call then).
5. For i in 0..m_maxTypeNum-1 (a SHORT): the CRE through one CCreatureFile
   for the whole call (CResHelper::SetResRef inlined: auto-request, warn if
   missing); a sprite with type 1, expiry m_lifeSpan * 15 + gameTime, the
   hunting and follow ranges, visible at all hours (0x7FFFFFFF), at the
   spawn point, facing 0; SetResRef from the file's resref, ReleaseData. A
   NULL sprite asserts (line 0x118) and continues with the next i. Then
   SetResRef again from the list entry, and the creature's m_nXP is added
   to the running total.
   - The first creature (i 0 with index 0) is placed without a budget
     check. Otherwise a total over the budget deletes the sprite (object
     array Delete, then the scalar deleting destructor only if Delete
     succeeded); at i 0 the loop restarts with i -1 -> 0 and index 0 (the
     rejected creature's power stays in the total), else it ends.
   - At i 0 the formation offsets come from m_group.GetOffsets(rand() % 9 +
     1, (direction * 360 / 16) % 360, TRUE), the direction being the
     sprite's GetDirection(ptFacingTowards) from the spawn point.
   - The square is the spawn point's search square plus
     offsets[i % 12] / 1000, through GetNearestOpenSquare with this
     object's terrain table, the animation's personal space and -1; the
     point is the square's centre.
   - If that point's tile is visible the sprite is deleted (Delete; delete
     if it succeeded and the pointer is not NULL), i is decremented and the
     loop ends: at i 0 that leaves i -1, so field_136 stays clear.
   - Otherwise AddToArea with the animation's list type, SetFacing toward
     ptFacingTowards, and a total equal to the budget ends the loop.
6. The offsets are freed; field_136 is set unless i ended negative (with no
   m_maxTypeNum it is set straight away).

So with any budget at least one creature spawns (the first, or the first of
the list after a rejected pick) unless a gate, m_maxTypeNum 0 or visibility
stops it; past that, creatures of the picked kind spawn while the running
total stays within the budget, up to m_maxTypeNum. A level whose budget
covers no creature still spawns exactly one and asserts nothing (Review
Focus 5, the [spawn][data] tests).

Original behaviour kept, with NOTEs in the code:
- The rejected creature's power stays in the total after the restart.
- SetResRef runs before the NULL check of the new sprite, as in
  CSpawn::ExecuteSpawn.
- The second SetResRef builds a CString from the 8-byte RESREF entry with
  CString::operator=(LPCSTR), so a full 8-character entry reads on into the
  next one; the resref keeps only 8 characters, so the visible result is
  the entry itself. Ours builds the CResRef from the 8 bytes (bounded).
- A sprite whose Delete fails is leaked.
- The level sum wraps in the BYTE (unreachable: six characters of level 30
  sum to 180).

Bounded (P4-10): the offsets array has max(members, 6) entries (GetOffsets
with bAtLeastSix), but it is indexed with i % 12 (FORMATION_MAX_SIZE,
0x847B22), so from i 6 a party of six or fewer reads past the heap block.
Ours reads (0, 0) for an index past the array: the spawn point's own
square, from which GetNearestOpenSquare searches.

No oracle case can compare it: it constructs sprites from CRE resources,
adds them to the object array and the area, and reads the game's party, the
visibility map and the search map. `spawn/spawn_point` is pending with that
reason; tests/test_gam.cpp's [spawn][data] tests drive it on AR1000.
