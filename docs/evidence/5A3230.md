## Notes

Ours is `CInfGame::Marshal(BYTE** pGame, DWORD* nGame, BOOLEAN
bProgressBarInPlace)` (`ret 0xC`; called by SaveGame with `a1 | a2`). Ported
from the disassembly: Ghidra's decompile is wrong past the `_alloca_probe`
(it mixes up the stack slots), so the notes below come from the
instructions.

Sizing pass: 0xB4 + 0x340 per party member plus each member's CRE data
(CGameSprite::Marshal, 0x70BEE0, into a stack array of six
CSavedGamePartyCreature), the same for `m_lstGlobalCreatures` in a heap
array, then the variables (`m_variables` vtable +0x0C, 0x54 each), the
journal (12 each) plus 400 for the familiar block, eight bytes per familiar
resref (`m_familiarResRefs[9][9]`, count at +0x0C of each list) and the
`field_4BDC` area-level records (4 + per record 0x1C + string length). The
progress steps are 2187500 / (party + globals) per creature and 312500 at the
end, or 0 and 2500000 when there is nobody. The slot whose sprite stands in
the visible area becomes `m_nPCAreaViewed` (the slot index, not the party
index).

Writing pass: "GAMEV2.2"; the header fields as in the instructions
(world time / TIMESCALE, current world area and link, the quick formations
copied from 4 down to 0 with `m_curFormation` set to the index whose value
equals the current formation, gold, weather flags, the flags 0x1 (no party
AI), 0x80 (area notes hidden), 0x20 and 0x40 (CScreenWorld +0x11F0, +0x11F4
clear), 0x10 (the world's UI manager hidden) and 0x6 when the first active
panel of 7 and 19 has an active control 0, version 3, reputation, master
area); the party table then each member's data appended and its
`m_creatureOffset` rewritten from the data pointer to the file offset; the
same for the global creatures; variables; journal (CGameJournal::Marshal);
the dword at file 0x6C (`m_storedLocationsOffset` in our header) takes
`m_cOptions.m_nNightmareMode`, as Unmarshal reads it back; the familiar
block (the 9 default resrefs, the list offset, 81 counts, then the resrefs);
the area-level records (`len + 0x18`, `len`, flags, the level as a dword
followed by 15 more bytes from +9 of the entry, the string at +0x1C).
Asserts at lines 4924 to 5238 with the original's condition texts.

`field_4BDC` holds `CInfGameAreaLevel` entries (new in CInfGame.h, the
layout from this function and Unmarshal); it was typed as `CString*` before.

Known gaps (outside this stream's files):
- CGameSprite::Marshal keeps the CRE data in the packed 32-bit
  `m_creatureOffset`. Ours resolves it as an `iwd2r::UnmarshalPtr` handle
  (compat/marshal_ptr.h); a handle the table does not know (a producer not
  yet converted) gives NULL, and the CRE bytes then stay zero instead of
  crashing (docs/64bit-cast-sites.md).
- `sizeof(CVariable)` is 0x58 in our build (CAreaVariable's double is aligned
  to 8 in FileFormat.h), the original's is 0x54; ours writes 0x58-byte records
  and Unmarshal reads the same, so the round trip holds but differs from the
  original's file layout.
- CVariableHash::Marshal never advances its output index.

No oracle case: it needs a whole game (object array, sprites, journal,
world screen). The round trip is pinned by tests/test_gam.cpp and
`world_entry` (SaveGame at Party Formation's Done, then LoadGame).
