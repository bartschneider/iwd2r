# 0x720B50 CGameSprite::sub_720B50

## Disassembly reading

- The function is ten near-identical per-sound-key loops (strcmp on the
  INI value name selects the loop). Each bundle loop begins `while(true)
  { iVar2 = -1; ... }` - the second IndexOf position (ours' pos2) is
  reset to -1 at the top of every iteration, then pos1 comes from
  FindOneOf(",") on v3 and pos2 from FindOneOf(",") on v4 only when v4
  is non-empty.
- objdump confirms the store is inside the loop: the first loop's
  back-edge `jmp 0x720C2F` lands three instructions before `or
  $0xffffffff,%edi` at 0x720C38, so pos2 (edi) is re-set to -1 every
  iteration. The fourth loop's decompile spells the same semantics in
  the empty arm (`iVar3 = -1` when v4 is empty, FindOneOf otherwise).
- Ours declared `INT pos2;` and only assigned it inside the non-empty
  branch: on the first pass it is indeterminate and on later passes it
  keeps the previous iteration's value once v4 runs out, so the
  `if (pos2 >= 0)` parse could consume garbage or a stale split.

## Notes

Imported the fork's `pos2 = -1;` after each of the ten `pos1 =
v3.FindOneOf(",");` lines (commit CGameSprite i017 import). His
placement sits after the pos1 scan instead of the exe's loop-top slot;
nothing between the loop top and that point reads pos2 and the IsEmpty
break exits the loop, so the two placements are behaviorally identical.
His ParseSoundEntry rename stays out (declaration lives in a header this
batch does not own).
