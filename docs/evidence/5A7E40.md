## Notes

Ported from the disassembly (`ret 0xC`, returns nothing; our declaration was
`BOOL`, now `void`). The version comes from the 8-byte signature:
"GAMEV2.1" is 21 (0x220-byte party entries), "GAMEV2.2" is 22 (0x340,
CSavedGamePartyCreature), anything else 20 (0x180); 20 is converted to 21 by
0x5A79E0 and 21 to 22 by 0x5A7BF0. The original game's ICEWIND2.GAM, which
NewGame loads, is "GAMEV2.0": no party, no globals, no variables, 100
inventory entries and an empty master area.

Order: world time (TIMESCALE * header) and CheckForTriggerEventPast; when the
service provider is the null one or we host, the current formation from the
quick formation it indexes and the five quick formations; current area and
link; gold; the nightmare-mode dword at file 0x6C (`m_storedLocationsOffset`
in our header) forces difficulty 5 (and the multipliers to 100 when hosting)
and writes "Difficulty Level" to the INI; area notes from flag 0x80;
reputation; progress (3000000 per party member past the first, 4374000 per
creature, 156250 at each step or 1250000 without creatures); 3000000 more
when there is a master area; the weather.

Global creatures: kept as the original has them, which is broken. The loop
condition is `count > 0` with no counter, it reads the party table's first
entry every time, and depending on the version one of the two entry pointers
it uses (0x5A833E reads `ebp`, the unmarshal at 0x5A8639 reads
`[esp+0x28]`) is still NULL. The original's game files have no global
creatures, so it never runs.

Then LoadArea(master area, 255, FALSE, bProgressBarInPlace) when the master
area is set; the CString is built from the resref bytes as a C string (the
out-of-line constructor 0x5A9660). Party loop: per entry,
`m_bPlayerScriptStyle` (0x37E1) is TRUE while the sprite is built (from the
CRE resource when a resref is set, line 7371/7373, otherwise from the entry's
data), SetResRef, AddActionTarget(0) past the first entry (as the original),
EnablePortrait, CGameSprite::Unmarshal(entry, TRUE, bProgressBarInPlace),
the visible area from the `m_nPCAreaViewed` member, a GetDeny without retry,
the XP caps for file versions 0 (89000) and 1 (161000), the named-creature
variable, ReleaseDeny. Then SelectToolbar, SetProtagonist(m_characters[0]),
ReputationAdjustment(100, TRUE) unless the version is 3, and, when hosting
with CBaldurChitin::field_4A24 set, the world screen's panel layout from the
flags 0x20, 0x40 and 0x10 (line 7462). Then the party inventory is skipped
(20 bytes per entry), the variables (`field_1B84` set around them, a
`m_bDisplayStale` and 60 ms sleep every 16), the journal, the familiars
(the default resrefs, then 9 x 9 counts), and, unless the version string is
"V1.1", the `field_4BDC` area-level records (the version test is the CRT's case-insensitive _mbsicmp, 0x7E8182). Ends with `cnt == nGame`
(line 7634).

Partial: the 0x40 flag branch also stores the view bottom at
CScreenWorld + 0x11FC, which our CScreenWorld.h lacks (TODO in the code).
Variables use `sizeof(CVariable)`, 0x58 in our build against the original's
0x54 (see 0x5A3230).

No oracle case: it needs a whole game (areas, sprites, world screen).
Pinned by tests/test_gam.cpp and `world_entry`.
