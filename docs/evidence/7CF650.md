## Notes

The 24-bit brightest blit of `CVidCell::Render`'s `0x8` branch (report-T50.md
section 2 group A/B; the only dispatcher/caller is 0x7AE5D0, call at
0x7AE903). It is the direct sibling of `sub_7CECD0`/0x7CECD0 and
`sub_7CF3F0`/0x7CF3F0: the same zero-size guard, the 24-bpp palette
realization (`Realize`, 24 bpp, fixed 255), the shadow-off palette entry from
the mode's `field_24`, the pitch in bytes (`lPitch - width * 3` once, added
after each row), three bytes written per pixel, and the same compressed run
walk with the same row-jumping accounting.

The difference is the composite: a drawn pixel keeps, per channel, the larger
of the destination's byte and the realized palette's. The compressed walk does
it straight from the palette dword (0x7CF7B1-0x7CF7CD):

```
edx = rgbTempPal[nColor]
cmp dl, [edi]      ; B
jb skip
mov [edi], dl
cmp dh, [edi+1]    ; G
jb skip
mov [edi+1], dh
shr edx, 0x10
cmp dl, [edi+2]    ; R
jb skip
mov [edi+2], dl
```

i.e. each of the three bytes is compared and written on its own (the write
also happens on equality, the same value). The raw walk (0x7CF806) reads and
writes a whole dword at the pixel - positions 0..2 compared, byte 3 stored
back unchanged - and handles the last pixel of each row with a word + byte
pair (0x7CF864-0x7CF8A7); the per-pixel form here writes the same bytes.

Unlike the 32-bit twin `Blt8To32Brightest` there is **no** frame-0
`field_174` block and **no** "palette colour is black" guard (`& 0xF0F0F0`) in
the compressed walk: the 24-bit compressed walk composites every drawn pixel.

Kept as the exe does: a zero-sized frame answers TRUE before any palette work
(0x7CF66C/0x7CF67A), and the transparent index is checked in both walks
(0x7CF76C compressed, 0x7CF80F raw).

`kind: oracle`: the case runs in the gate on our Windows rig (the run below).
`tests/test_vid.cpp` ("blt8to24_brightest") pins the per-channel max, the
shadow-off palette entry and the zero-size return in the harness's own terms;
against the stub 8 of its 26 assertions fail.
