# 0x787F20 CDimm::Request

## Disassembly reading

- Lock-count preamble: the exe takes the field_2FC critical section only
  when both field_44 and field_40 are zero (0x787f2a), clears
  RES_FLAG_0x08 with its RemoveAt, re-lists RES_FLAG_0x04 entries through
  the PRIORITY switch onto m_lServicedHigh/Medium/Low, parks the others on
  m_lRequestedHigh/Medium/Low, and leaves the section; then bumps
  `pRes->field_44` unconditionally (`mov %ebp,0x44(%esi)` at 0x788000).
  Ours writes the same order.
- Range guards: `(id >> 20) < m_nResFiles` and `(id & 0xFFF00000) <
  0xFC000000` are unsigned `jae` skips at 0x788013/0x788025 - ours.
- 0x788031: `mov (%ecx,%eax,4),%ebp` loads pResFile from m_ppResFiles; the
  function runs FPO-style with ebp holding pResFile, so `0x8(%ebp)` below
  is m_nRefCount, not a stack parameter.
- The cache spin: EnterCriticalSection on g_pChitin+0x35C (field_35C),
  `lea 0x632(%eax)` = g_pChitin+0x542+0xF0 = &cDimm.cResCache, sleep loop
  on pResCache->field_110 - ours step for step.
- The refcount guard at 0x7880a4 is `cmp $0,0x8(%ebp)` / `ja 0x7880b3`
  over `m_nRefCount = 0; call 0x78a2f0 (OpenFile)` - the canonical MSVC
  encoding of source-level `m_nRefCount <= 0` on an unsigned member (the
  negated `>U 0` branch). The Ghidra decompile flattens this to `== 0`;
  the instruction encoding is the wider `<= 0` guard, which is what ours
  writes. m_nRefCount += 1 and LeaveCriticalSection(field_35C) close the
  block as in ours.
