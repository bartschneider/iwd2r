## Notes

`CUtil::FindOneOf(const CString& sString, const CString& sSeparators, int
start)` (__cdecl, plain `ret`; the separators are copied (0x7FC98F, the copy
constructor) into their argument's slot at 0x7811A5). The index of the first character of `sString` from
`start` that is one of the separators, else -1.

With Double Byte Character Support on (g_pChitin 0x8CF6D8 + 0x1A0):
- the separators lose every lead byte (Left + Mid, 0x7811DE-0x781266), and
  an empty result gives -1 (0x781275). NOTE: the original bounds this loop
  by the length before any removal (`ebp`, 0x7811CD, reloaded at 0x781261),
  so after a removal it reads past the separators' end; ours stops at the
  current end (bounded, ruling P4-10);
- in the search, a lead byte of the searched string skips its trail byte
  (`IsDBCSLeadByte([ebx][edi])`, 0x78129C-0x7812B9).

Fixed in round 2 of the ui-misc stream: ours tested
`IsDBCSLeadByte(separators[index])`, the separators' byte at the searched
string's index, and without checking the flag, reading past the
separators' end on every long search. On Linux IsDBCSLeadByte was always
FALSE, so results were right; with a double-byte code page a trail byte
equal to a separator matched.

Tests: tests/test_ui_misc.cpp "util: FindOneOf skips a double-byte
character of the searched string" (single-byte searches; Shift-JIS lead
bytes through the new test hook iwd2r_SetTestLeadBytes in
platform/win32_stubs.cpp: the trail byte skipped, the separators' lead
bytes removed). It fails on the old test.
