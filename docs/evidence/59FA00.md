handling (platform/replay_clock.h FrameGate, tool-deterministic-loads).

The deadlock claim rests on the wait loops above. Every branch spins with
`SleepEx(5)` on `*(g_pChitin + 0x193E) == 1` (`m_bInSynchronousUpdate`)
and/or `*(g_pChitin + 0x193A) == 1` (`m_bDisplayStale`); the branch where
this thread owns the visible area's list lock waits for `m_bDisplayStale`
and, with the argument set, for `m_bInSynchronousUpdate`. CChitin::WinMain
(0x7926B0) sets `m_bInSynchronousUpdate` to 1 just before it calls
SynchronousUpdate through vtable slot 0 (`call [edx]` at 0x79284B; slot 0 is
CBaldurChitin::SynchronousUpdate 0x425FB0, whose first instruction is the
recorder's frame hook) and back to 0 after it. So while the frame hook runs,
this function cannot return: a hook that waited there for the load to finish
would deadlock. The gate holds the call and returns instead.

The callers listed are the load paths (DestroyGame, NewGame, LoadGame,
LoadArea, SaveGame, the progress-bar callbacks, OnMainDoneButtonClick);
they run on the AI thread inside one AsynchronousUpdate, which is why the
load's frames are drawn while `m_bInAsynchronousUpdate` is set (0x4242B0).
The progress bar flag the dump reports as `globals.loading` is
`*(g_pChitin + 0x1986)`, `cProgressBar.m_bProgressBarActivated`, set and
cleared only by CBaldurChitin::SetProgressBar (0x425710).

No oracle case: it needs a running main thread, the game's area and the
display flags; `tools/oracle.py replay record scenarios/world_entry.txt`
exercises it in every load.
