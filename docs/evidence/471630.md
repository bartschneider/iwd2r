## Notes

Ours is `CGameArea::Marshal(BYTE** pArea, DWORD* nArea, BOOLEAN
bProgressBarInPlace)` (`ret 0xC`), declared in CGameArea.h (it was absent).
Ported from the disassembly with Ghidra's decompile for the switch tables
(each confirmed against the jump tables at 0x472C20, 0x472C8C, 0x472CFC,
0x472D60).

It empties `field_AAA` (a list at 0xAAA, between `m_lTiledObjects` and
`m_ptOldViewPos`, now declared; nothing in our tree fills it), sets the
progress unit to PROGRESSBAR_AREA_ADDITIONAL / 25, and when a session is
open and we are not hosting only reports progress. Otherwise it walks four
object lists from the tail, by object type (switch values are the
CGameObject::TYPE_* bytes): `m_lVertSortFlight` (0x9CA: sounds, spawning
points, creatures), `m_lVertSort` (0x992: doors, statics, creatures,
triggers), `field_AAA` (GetDeny; creatures) and `m_lVertSortBack` (0x9AE:
containers, sounds, spawning points, creatures, triggers). A creature with
`m_bGlobal` (0x4C52) is skipped except in the flight list. The asserts carry
lines 4317 to 4524 as the original's.

The size is the header (8 + 0x5C), offsets (0xC8), sounds-and-music (0x90),
rest encounter (0xE4), the entry points (0x68 each), the user notes (0x34
each), the visibility map, the variables and every marshalled block; the
blocks are written in the original's order: visibility, statics, sounds,
spawning points, creature data then the creature table, points (containers,
then each door's four point sets, then triggers; each `*Start` becomes a
point index), doors, triggers, items, containers, variables, entry points,
user notes (CGameAreaNotes::Marshal), and the area script's resref from the
area AI object's `m_movementScript` (0x40E). `m_lastSaved` takes the world
time / TIMESCALE. Assert `cnt == (DWORD)*nArea` at line 4913.

Partial (outside this stream's files):
- For the master area the original first calls 0x5170F0 on the game's
  `m_cMoveList` and `m_cLimboList` with `this`, right after `field_AAA` is
  emptied; the 0x471757-0x4717A5 sequence is ported (the calls at 0x471788
  and 0x4717A0), so a save carries the sprites in a pending move.
- The door, container, creature and trigger marshals keep their data in
  packed 32-bit fields. Ours resolves those as `iwd2r::UnmarshalPtr` handles
  (compat/marshal_ptr.h) at the eight sites listed in
  docs/64bit-cast-sites.md; an unknown handle gives NULL and the block stays
  zero.

No oracle case: it needs a loaded area and its objects. Run by SaveGame in
`world_entry`.

M2 dump (filed by hand, header changed): `src/CGameArea.h` had
m_lVertSortFlight at 0x099A, inside m_lVertSort. Marshal walks four lists
tail to head (`node = *(this + tail)`, `id = *(node + 8)`, `node = *(node +
4)`, the count at tail + 4): tail 0x9D2 / count 0x9D6 (the list at 0x9CA,
the first loop, which ours ports as m_lVertSortFlight), 0x99A / 0x99E (0x992, m_lVertSort:
doors, statics, sprites), 0xAB2 / 0xAB6 (0xAAA, field_AAA) and 0x9B6 / 0x9BA
(0x9AE, m_lVertSortBack). The lists are 0x1C bytes apart (MFC 4.2's 32-bit
CPtrList: vtable, m_pNodeHead +4, m_pNodeTail +8, m_nCount +0xC,
m_pNodeFree, m_pBlocks, m_nBlockSize), so m_lVertSortFlight, between
m_lVertSortBack (0x9AE) and m_lVertSortAdd (0x9E6), is at 0x09CA: the comment
is corrected, the member order unchanged. Doors are on m_lVertSort only
(CGameDoor's constructor adds them with LIST_FRONT); TYPE_SPRITE (0x31)
objects are on all three. The dump's `world.doors` walks m_lVertSort head to
tail (`m_pNodeHead`, CNode `pNext` at +0, `data` at +8) and
`world.creatures` counts the sprites on m_lVertSort, m_lVertSortBack and
m_lVertSortFlight: fields `area_vert_sort` (0x0996), `area_vert_sort_back`
(0x09B2), `area_vert_sort_flight` (0x09CE), `list_node_next` (0x00),
`list_node_data` (0x08).

Triggers (objid stream, M2-6): the trigger cases of the front and back
lists call 0x4CFF70 (`CGameSprite_B3AUTO_004cff70` above, our
CGameTrigger::Marshal, ported in src/CGameTrigger.cpp), add the block to the
trigger list and count its pick points (`+ *(ushort *)(block + 0x2a)`,
`m_pickPointCount`). Ours skipped them, so an area reloaded from a save
(Party Formation's Done saves and reloads AR1000) lost its 17 triggers and
every later object id moved down by 17. tests/test_gam.cpp ("SaveGame packs
AR1000 into ICEWIND2.SAV ...") saves and reloads AR1000 and compares the
object counts by type.
