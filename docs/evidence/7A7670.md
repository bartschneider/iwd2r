# 0x7A7670 CNetwork::SlidingWindowReceive

## Decompiled

Driver bundle row 0x7a7670 (`CNetwork_B3AUTO_007a7670`). The port
is anchored on the exe bytes (see exemption). What the exe does,
in order:

1. Fetches a frame with `FetchFrame(dpIDFrom, dwSize)` and exits
   the function when no frame comes back (NULL).
2. A frame from the system player (`dpIDFrom == 0`, DirectPlay's
   `DPID_SYSMSG`) goes straight to `HandleSystemMessage(pData,
   dwSize)`, then the buffer is freed.
3. An application frame shorter than 10 bytes is rejected (freed)
   — it cannot carry the 4-byte trailing CRC.
4. Otherwise the received CRC is composed big-endian from frame
   bytes 6-9, those four bytes are zeroed, and the expected CRC is
   recomputed over the whole frame through the `m_dwCRC32` table.
5. A CRC mismatch frees the buffer. A match walks the six player
   slots and, for every slot whose id equals `dpIDFrom` (and is
   non-zero) with an initialized sliding window, dispatches
   `m_pSlidingWindow[nPlayer].ReceiveCall(pData, dwSize)` and
   marks the frame consumed.
6. An unconsumed frame is freed; then the loop fetches the next
   frame, until `FetchFrame` returns NULL.

## Notes

The assert is unreachable in the exe on this path — `dpIDFrom !=
0` was already proven by the branch at 0x7a769e — but the compiler
still emits the `test edx,edx; jne` guard at 0x7a774e because the
source asserts unconditionally inside the player loop. The port
preserves the source-level assert in the same position.

The player loop does not stop after the first match: `bDeleted` is
set but the six iterations continue, and every matching slot with
an initialized window receives the frame. Ids are unique across
slots in practice, so at most one dispatch happens per frame; the
port keeps the loop's full sweep either way.

Frame layout implied by the CRC handling: bytes 6-9 are the CRC-32
of the frame with those bytes zeroed, stored big-endian (byte 6 is
the most significant). System frames skip the CRC entirely and
also bypass the `dwSize >= 10` gate.

The exit path (0x7a77bf) is reached both from the first-fetch NULL
test — before `ebp`/`edi` are pushed — and from the loop-tail NULL
test, which pops them first (0x7a77bd-0x7a77be); the shared
`pop esi; pop ebx; add esp,0x10; ret` keeps the stack balanced in
both cases, which the port's single-exit `while` shape mirrors.
