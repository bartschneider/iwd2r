## Notes

Filed by hand for the replay dump's `world` block (M2: doors, dialog,
party actions, explored tiles, creatures; oracle/replay/schema.json,
x-fields): `tools/gen_fields.py` takes these offsets from the `/* NNNN */`
comments of our headers, which `tools/check_evidence.py` does not check, and
the recorder reads them from the original's memory. This is a function that
reads the layout.

Header changed: `src/CGameDoor.h` gains `/* 0610 */ SCRIPTNAME
m_scriptName`. The constructor copies the ARE door record's name
(`_strncpy(this + 0x184 * 4 = this + 0x610, pDoorObject, 0x20)`) into the
door's own 32-byte member after CTiledObject m_tiledObject (0x5F8, 0x18
bytes), not into CGameAIBase::m_scriptName (0x554). Our header had no member
there, so our door wrote its name into CGameAIBase::m_scriptName; the new
member hides that one, so ours now writes and reads the name where the
original does (CGameDoor::Marshal, 0x48ADC0, copies it back from 0x610).
Field `door_name` (i8 x 32, 0x0610), the dump's `world.doors[].name`.

`in_ECX[0x171]` (0x5C4) is m_dwFlags, from the record's flags (+0x28); bit 0
picks the open or closed search squares and AddToArea position (`& 1`), so
`world.doors[].open` is bit 0. Field `door_flags` (u32, 0x05C4).

`*(byte *)(this + 4) = 0x21`: CGameObject::m_objectType (0x0004) is
TYPE_DOOR, the byte the dump matches doors by (field `object_type`).

The closed search squares' count is the record's `m_closedSearchSquaresCount`
(+0x4E, `mov dx,[edi+0x4E]` at 0x485C48 and `mov ax,[edi+0x4E]` at 0x48635B),
not the open count (+0x4C) our port read. With the open count a closed door
marked the wrong number of squares in the search map's dynamic cost (0x80),
so line of sight (CGameArea::CheckLOS through CSearchBitmap::GetLOSCost) and
paths could cross some closed doors. Found through the rand trace of
walk_and_talk (rng round 3): AR1000's Door_Hint_Text_01 saw the party through
a closed door at frame 1496 (CGameSprite::CheckIfVisible), so its AI
inhibitor was cleared in frame 1498 and it ran a ProcessAI the original did not.

## Polygon set-up (render round 9)

A point is dropped only when it lies on the line through its two
neighbours. With x2,y2 two points back, x1,y1 the previous point and x0,y0
the current one, it goes when:

- x2 == x1 == x0, or y2 == y1 == y0; or
- x2 != x1, x1 != x0, and 1000*(y2-y1)/(x2-x1) == 1000*(y1-y0)/(x1-x0)
  (idiv truncation).

The equal-slope case is `cmp eax, <slope>; jne <keep>` at 0x486031 for the open polygon (+0x5C8, count +0x5CC) and 0x4861D0 for the closed one (+0x5CE, count +0x5D2). Dropping
copies the current point over the previous one and counts it in `adjust`,
as ours does.

Fixed: ours compared the slopes with `!=`, so it dropped the middle point
whenever the two slopes *differed*, that is almost every point. Every AR1000 door's open polygon kept 2 of its 3 points. AR1000
now keeps 292 points in its triggers, doors and containers, the count the
original saved (Probe Save of the crossload run 20261016-171655). Ours kept
133. The only point dropped is one of Barrel Three's ten. The test checks
all 54 polygons against that save.

## Bounding rectangles (render round 9)

The open rectangle (+0x5A0) and the closed one (+0x5B0) take left and top
from the file (+0x38, +0x3A; +0x40, +0x42). Right and bottom are one past
the file's (+0x3C, +0x3E; +0x44, +0x46, each `inc` before its store, at
0x485CA6, 0x485CB3, 0x485CD6 and 0x485CE1). Marshal (0x48ADC0) writes them
