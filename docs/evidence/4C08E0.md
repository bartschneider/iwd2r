## Notes

CGameEffectList::RemoveAllOfType: removes and deletes (after OnRemove, vtable +0x24) every effect of the given id (and amount, unless -1), skipping the node to leave; when the node before the one to leave is visited, m_posNext becomes the node after it (0x4C0979). An empty list (m_nCount 0) stops the walk.

Original bug bounded (ruling P4-10): after skipping the node to leave, ECX still holds that node, so a matching effect right after it makes the original RemoveAt the node to leave (0x4C0946) and delete the matching effect while its node stays in the list (a dangling pointer). The port removes the matching effect's own node.

## WSO body (undecided in b019)

b019 leaves this row undecided (no verdict line, ours kept):

- The original's second filter compares the argument against the effect at
  runtime offset +0x1c — m_dwFlags in our layout, because CGameEffectBase
  declares no vtable, so runtime member offsets sit one pointer above the
  header comments (the opcode match at +0xc = m_effectID confirms the shift;
  our own engine keys portrait icon ids off m_dwFlags, src/CGameEffect.cpp:1919).
  The wave's body matches m_dwFlags; ours matches m_effectAmount, which is
  wrong.
- But the wave's node handling deviates from the original on reachable paths:

  removal, where the original only breaks when posLeave is the last node, can
  remove the posLeave node itself (ECX still holds it, 0x4C0946), and writes
  m_posNext once after the loop. Ours has the original's structure.

Neither body is adopted; deciding this needs an effect-object probe case
(drive RemoveAllOfType over a two-effect list with posLeave in the middle).
